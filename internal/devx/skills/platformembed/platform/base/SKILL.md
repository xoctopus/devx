## 文档

> 该章节在编写修改所有文档(包括代码注释)时使用

1. 每个领域/模块包应该有 `doc.go`. 描述领域概况和对外契约用法.
2. 中文英文选择按照仓库惯例
3. `doc.go`, `*.md` 文档如果是中文, 使用半角标点, 切勿使用全角标点.
4. `*.md` 注意表格对齐并控制表格宽度, 避免表格过宽影响阅读.

## 提交信息

> 该章节在帮助用户总结提炼仓库变更, 生成提交信息时使用

1. 遵循 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) 规范
2. 中文英文选择按照仓库惯例
3. 如果是中文, 使用半角标点, 切勿使用全角标点.
4. 多个改动点提交格式例子如下: summary 和 detail 需要提炼重点, 切勿啰嗦.
5. 给两个结果 1) 命令行 2) 提交信息文案
6. 通常不要主动做提交动作, 除非明确要求

> 例子

```
git commit -m "feat(module): summary mainly" \
-m "- change detail 1
- change detail 2
..."
```

## 代码精简

> 该章节在帮助用户完善/生成代码时使用

1. **YAGNI**: 只实现当前明确需要的逻辑; 不为"以后可能用到"预留抽象, 接口或参数.
2. **扁平**: 直接调用与顺序逻辑优先; 单一实现不必套设计模式.
3. **惯用法**: 优先标准库与语言惯用写法, 少样板; 卫语句提前返回, 合并重复分支; 一次性临时变量能省则省. 同一函数内 **对称、短小的重复步骤**(如两段相同的前处理+校验) 若内联更清晰, 不必为 DRY 单独抽函数.
4. **命名与注释**: 名短意清, 少 `Impl`/`Factory` 等修饰; 除非显然的业务或不变量外, 不写注释.
5. **重构**: 先问能否删掉, 再加包装. 单一职责指 **模块/类型边界**, 不是把同一函数里对称的几步各抽成 helper; 控制 **文件/类型** 体量, 不追求函数行数越少越好.
6. **可读与复用**: 跨函数复用时, 以「读者少跳转、语义不混淆」为前提. 默认在调用处平铺; 仅当同一规则在 **两处及以上** 仍完全一致, 或抽函数后主流程 **在一屏内读完** 且名字能准确表达差异时再抽. 规则相近但不相同(如是否 upper、额外校验)时, 不要共用同一 helper 名, 避免读起来像同一类 API.

输出代码前自检 (任一项为是, 按对应项改完再输出):

1. 是否仍用手写逻辑, 而标准库已有等价能力?
2. 是否 **仅为 DRY** 拆了只用一次、内联更清楚的小函数? (不含 **≥2 处** 调用或包级对外 API)
3. helper 名是否容易与邻近函数 **混淆规则** (读者会误以为语义同级)?
4. 是否带有当前用不到的配置或字段?

> 1/4: 删减或换标准库. 2: 内联, 或等到第二处真相同再抽. 3: 改名或拆开规则, 勿与邻近 API 混名.
